# Workflow orchestration implementation

The active catalog is generated by `scripts/generate-workflows.mjs` from
`scripts/workflow-catalog-source.json` and the twelve role profiles. Run the
script after editing these sources; `--check` detects stale generated documents.
`starter/catalog.json` is consumed by both frontend and native registration.
Historical snapshots live in `starter/legacy` and retain exact-match migration
semantics, so customized user workflows are not replaced.

## All fifteen workflows

| Workflow ID | Execution order | Main acceptance focus |
|---|---|---|
| plan-build-verify | Plan → task queue → Verify | Whole-request criteria and integration |
| investigate | Research → Analyze | Sourced findings grounded in code |
| design | Architect → Plan | Interfaces, alternatives, executable tasks |
| diagnose | Debug → Plan | Reproduction, root cause, regression criteria |
| implement | Plan → task queue → Verify | Reconcile approved plan and amendments |
| security-audit | Security → Plan | Concrete findings and remediation criteria |
| check-changes | Review → Verify | Inspect defects before expensive checks |
| analyzed-feature | Analyze → Plan → task queue → Verify | Existing behavior and change surface |
| researched-feature | Research → Architect → Plan → task queue → Verify | External assumptions and integration |
| bug-fix | Debug → Plan → task queue → Verify | Reproduction and regression coverage |
| careful-change | Analyze → Plan → task queue → Verify → Review | Whole-change correctness and regressions |
| security-remediation | Security → Plan → task queue → Verify → Security | Every original security finding |
| refactor | Analyze → Plan → Refactor queue → Verify → Review | Observable behavior preservation |
| optimize-performance | Analyze → Plan → Optimize queue → Verify | Comparable baseline and after measurements |
| documentation | Analyze → Plan → Document queue → Verify → Review | Examples, commands, links and source accuracy |

Read-only assessments can finish with findings; their `complete` status means
the assessment is finished, not that the inspected software is defect-free.
Editing workflows require a passing verdict and evidence for every criterion.

## Runtime contracts

- A plan names every requirement, observable criterion, bounded task and earlier
  dependency. The runtime rejects missing coverage, duplicate IDs, forward or
  cyclic dependencies, and plans outside 1–128 tasks.
- Every task uses fresh builder and reviewer sessions. The reviewer receives a
  strict inspection-only tool scope. Preparation outputs remain available.
- Progress is committed before continuing: accepted tasks, the current build,
  review findings and processed rejection count. Failed-run continuation retains
  accepted tasks, and repair attempts receive the last unfinished attempt.
- Each task has up to two local repair/continuation attempts. Downstream failures
  reopen the earliest affected task and later tasks; environment/user blockers
  terminate without the automatic repair loop. The graph allows three build
  attempts and 40 total graph-step attempts. Existing optional usage limits are
  enforced during execution as well as at step admission.
- Final acceptance rejects absent, duplicate, failed and unevidenced criterion
  results. These are structural checks; factual correctness still depends on
  inspection, executed tests and model judgment. A model can still omit a
  requirement when constructing its plan; this is not a formal proof of scope.

## Context and effective prompts

Every built-in has access to `read_workflow_context`, a paged source containing
the preserved user/assistant conversation and handover. Bounded display/context
summaries remain, but no longer represent the only available copy. Profiles
contain role boundaries; nodes own scope and response schemas. Earlier source
text and model reports are explicitly treated as evidence, not instructions.

Workflow requests opt in to `ModelRequestPrepared` tracing. This captures the
native execution request after profile/rule/final-turn instructions are applied,
just before backend dispatch. The trajectory stores redacted, numbered JSON
parts rather than truncating long prompts. Concatenate `content` in `part` order
for a `traceId` to inspect the complete redacted request. Provider-specific wire
conversion or provider-side instructions are outside this trace. It is not
proof that a provider has no additional instructions.

## Check execution

Shell tools now receive the same cached login-shell PATH as the native host,
addressing GUI launches that could not locate npm/cargo. Missing executables
produce a blocker instead of repeated installation attempts.

Run-local check receipts bind success to commands, test selection and a stable
workspace fingerprint, including untracked files, dependencies and Git metadata.
Writes, installations and arbitrary commands invalidate receipts; failed fresh
checks discard old receipts. Unknown/oversized/external-linked snapshots disable
reuse. Evidence expires after five minutes and is never reconstructed from model
prose. `fresh` bypasses reuse. Service-dependent checks and external state require
fresh execution; a local fingerprint cannot prove their inputs are unchanged.

## Validation and limits

Regression coverage includes multi-task execution, local repair, failed-run
checkpoint round-trip, retaining accepted tasks, fresh delegated runs, usage
budget cancellation, criterion rejection, full context pagination, full prompt
trace persistence/redaction, check invalidation, and historical migrations.
Native tests also compile all fifteen workflows and register all twelve profiles.

The implementation has automated validation, not a live-provider quality or
latency benchmark. There is no measured speedup claim. Failed runs can continue
from saved progress; manually cancelled runs retain snapshots but the existing
chat continuation UI still accepts failed runs only. Ordinary completion gates
prove tool activity, not that every potentially applicable check was executed.
The final verifier must choose and report the relevant check set.

Validation on 2026-10-02: 1,912 frontend tests; 122 runtime, 130 core,
44 session-store and 203 native tests passed (four native tests ignored).
Production and test TypeScript checks passed. IDE and website production builds
passed. Frontend tests/build used the installed Node 22.23.1 because the shell's
Node 22.1.0 is below this project's declared minimum. After the final receipt
invalidation and test-type corrections, the 128 affected tests passed again.
